| Prompt Name | Actual Prompt Text | My Reflection |
|---|---|---|
| Draft Specification | "Draft docs/lab-03/specification.md extending the Lab 2 contract: authentication, authorization, DevRequester→User migration, IT Staff workflow, and Administrator user management. | Review Specification | "Act as a specification reviewer for specification.md. | Draft Test Plan | "Draft docs/lab-03/tests.md covering unit, API, UI, authorization, migration/regression, and E2E levels." | Listing unit, API, UI, authorization, migration/regression and E2E levels up front gave every acceptance criterion at least one planned test, so later I could check evidence against the plan instead of trusting a "done" claim. As in Lab 2, the traceability table was the most useful artifact. |
| Implement Authentication | "Implement login, logout, current-user, and mandatory password change per the approved contract. Migrate DevRequester rows into User with role=REQUESTER in place, keeping the same ids, without losing ticket ownership." | Making the AI implement the migration in place (same ids, no lost ticket ownership) turned the schema change into something I could verify with a dedicated test (API-18) and the Lab 2 regression suite. Both are cheaper than discovering broken ownership in the UI. |
| Implement IT Staff Queue | "Implement GET /api/staff/tickets and the Ticket Queue screen with search/filter/sort/pagination, accessible to IT Staff and Administrator." | The queue is a good example of server-side filtering and pagination, shared by IT Staff and Administrator. The later E2E run showed that the generated tests assumed UI labels the component did not have ("Search tickets"). The fix was an accessible name on the input, which also benefits screen-reader users. |
| Implement IT Staff Ticket Operations | "Implement claim/reassign ownership, IT Priority, permitted status transitions, Public Comments, and Internal Notes, enforcing the BR-12 transition matrix server-side." | This prompt carries the core security rules: the BR-12 transition matrix, the separation of Public Comments from Internal Notes, and IT Priority reserved for staff. Enforcing them server-side meant they could be tested directly through the API, not just by hiding buttons. |
| Implement Administrator User Management | "Implement the minimalist User Management screen and API per the contract, including the self-deactivation and last-Administrator safety rules." | The self-deactivation and last-Administrator rules are easy to enforce only in the UI. Putting them in the API as well, and testing both layers (API-16 and E2E-03), meant a direct request cannot bypass them. The E2E suite also exposed a race in the Requester test: it asserted and reloaded the page before the login had finished, so the session cookie was not yet set and the app showed the login page. The fix was to wait for the post-login URL first. |
| Completion Review | "Audit the implementation against every acceptance criterion and planned test, including direct API authorization checks for every protected endpoint. Report missing evidence before claiming completion." | The completion review should include direct API authorization checks for every protected endpoint, not only UI tests. In the first full Playwright run 33 of 39 tests passed; the 6 failures (two root causes, three viewports each) were a missing accessible label and a login race in a test. Neither would have been caught by a "looks done" claim. |

## Reflection
_Authorization testing changed my approach compared to Lab 2. There, hiding something in the UI was enough to look correct; in Lab 3 every protected rule (Requester vs Internal Notes, staff and admin endpoints, IT Priority, self-deactivation) is also tested directly against the API, because a passing UI test is never proof of a security control. The in-place migration from DevRequester to User taught me to evolve a schema without breaking existing data: keep the same ids, migrate rather than recreate, and prove ticket ownership survived with a regression test. The E2E runs also showed that AI-generated tests are only trustworthy once run against the real app: the first run had 6 failures from two causes (a missing accessible label, and a test that reloaded the page before the login finished). Next sprint I would run the E2E suite as soon as each screen is generated instead of at the end._
