# Lab 2 Sprint Engineering Specification — TokTickIT Requester Ticketing MVP

## 1. Sprint Goal
Deliver a Requester-facing MVP of TokTickIT: a Requester (simulated via a temporary
Development Requester selector) can create an IT support ticket with attachments,
find and review their own tickets in a searchable/filterable/sortable/paginated list,
and inspect a single ticket's details and attachments. This sprint also establishes
the Zen Green UI foundation and the data/API conventions that later sprints
(IT Staff workflow, authentication) will build on.

## 2. Stakeholder Request Interpretation
The IT department wants a professional, responsive self-service ticketing screen
for end users. A Requester must describe a problem (category, related system,
summary, description, requested priority), attach evidence, and submit it. After
submission they must be able to find that ticket again, browse and search their
own ticket history, and inspect/manage its attachments — without ever seeing another
Requester's tickets. Because real login isn't built until Lab 3, a temporary
"Development Requester" picker simulates being logged in as one of several seeded
Requesters, purely for testing multi-user ownership.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism only)
- Create Ticket: form, validation, attachment upload, Ticket Number generation
- My Tickets: paginated list scoped to the current Requester, search, filters, sorting
- Requester Ticket Detail: read-only ticket header + attachment list
- Attachment lifecycle: add to existing ticket, download active attachment, soft-remove
  with reason
- Ownership protection on every Requester-scoped endpoint
- Zen Green UI foundation: shared tokens, form/list/badge/state conventions,
  responsive layout rules

### Excluded
- Authentication, sessions, passwords, tokens, real authorization (Lab 3)
- IT Staff dashboard, ticket assignment, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any status transition beyond the initial `NEW` status (no resolve/close/reopen)
- Administrator functions (user/category/related-system management UI)

## 4. Functional Requirements
- FR-01: The system shall require a Development Requester to be selected before any
  ticket screen is accessible.
- FR-02: The system shall let the selected Requester submit a new ticket with
  category, related system, summary, description, requested priority, and 0–5
  attachments in one submission.
- FR-03: The backend shall generate a unique, human-readable Ticket Number for every
  successfully created ticket.
- FR-04: The system shall let the selected Requester view a paginated list containing
  only tickets they own.
- FR-05: The system shall let the Requester search by ticket number/summary and
  filter by category, requested priority, and current status.
- FR-06: The system shall let the Requester sort the ticket list by at least ticket
  number, created date, and last-updated date, ascending or descending.
- FR-07: The system shall let the Requester open a Ticket Detail screen for a ticket
  they own.
- FR-08: The system shall let the Requester add a new attachment to an existing
  owned ticket, subject to the fixed attachment rules.
- FR-09: The system shall let the Requester soft-remove an attachment they own,
  recording a removal reason.
- FR-10: The system shall prevent a Requester from retrieving, downloading, or
  modifying a ticket or attachment owned by a different Requester.
- FR-11: The system shall present distinct empty ("no tickets yet"), no-results
  ("no tickets match your filters"), loading, and error states on every data-bound
  screen.

## 5. Business Rules
- BR-01: The official Ticket Number is generated by the backend, using the format
  `TKT-{YYYY}-{6-digit sequence}` (e.g. `TKT-2026-000042`). The sequence resets to
  `000001` at the start of each calendar year (based on `createdAt`'s year); the
  full `ticketNumber` string is globally unique. Generation must be safe under
  concurrent requests (e.g. a DB transaction computing `MAX(sequence) + 1` for the
  current year, or a dedicated per-year counter row, guarded by a unique constraint
  retry).
- BR-02: A new ticket always starts with `currentStatus = NEW`. `itPriority` is
  nullable and left unset in Lab 2 (IT Staff sets it in a later lab).
- BR-03: The Development Requester selector is a **testing mechanism, not
  authentication**. The selected `requesterId` is stored in `sessionStorage` (cleared
  when the browser tab/session ends, so every new session must re-select a
  Requester) and sent with every request via the `X-Dev-Requester-Id` header; it
  must never be described as a secure identity.
- BR-04: Only Requesters with `isActive = true` appear in the Development Requester
  selector.
- BR-05: Changing the selected Requester immediately invalidates and reloads all
  requester-scoped data (My Tickets, any open Ticket Detail is re-checked for
  ownership on next access).
- BR-06: A ticket belongs to exactly one Requester, fixed at creation time; ownership
  never changes in Lab 2.
- BR-07: `summary` is required, trimmed, 5–120 characters. `description` is required,
  trimmed, 10–2000 characters. Both are validated on the frontend and re-validated on
  the backend.
- BR-08: `category` and `relatedSystem` must reference existing, active reference-data
  rows; unknown or inactive IDs are rejected with a validation error.
- BR-09: The submit control is disabled immediately on click and re-enabled only after
  the request resolves, to prevent duplicate ticket creation from repeated clicks.
- BR-10: If ticket creation fails validation or server-side, all entered field values
  remain in the form so the Requester does not have to retype them.
- BR-11: Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF; maximum size is
  5 MB per file; a ticket may have at most 5 **active** (non-removed) attachments at
  any time.
- BR-12: Removing an attachment is a soft removal: the row is kept with
  `isRemoved = true`, `removedAt`, and `removedReason`; the metadata stays visible in
  the UI but the file becomes non-downloadable and non-previewable.
- BR-13: If the ticket record saves successfully but one or more attached files fail
  to upload, the ticket is still created; the response reports which files failed so
  the Requester can retry adding them from Ticket Detail. There is no automatic
  rollback of the created ticket.
- BR-14: An empty ticket list distinguishes "you have no tickets yet" (zero tickets
  ever) from "no tickets match your current search/filters" (zero after filtering a
  non-empty set).
- BR-15: Every Requester-scoped lookup (ticket, attachment) verifies that the
  resource's `requesterId` matches the current `X-Dev-Requester-Id`; a mismatch
  returns `404 Not Found` (not `403`) so the requester cannot infer that the resource
  exists.
- BR-16: An inactive Requester can never be selected and, if somehow selected (e.g.
  stale client state), every requester-scoped request is rejected with `401`.
- BR-17: The `requesterId`-based ownership model is designed so that Lab 3 can replace
  the `X-Dev-Requester-Id` header with a session-derived requester identity without
  changing the Ticket/Attachment schema.

## 6. UI Specification Summary
See `docs/lab-02/ui-spec.md` for full detail. Summary:
- **App shell**: TokTickIT header (Zen Green primary `#006B3C`), My Tickets / Create
  Ticket navigation, current Development Requester name + "Change Requester" action.
- **Development Requester Selection**: dropdown of active requesters, loading/empty/
  error states, Continue button, explicit "testing only, not login" messaging.
- **Create Ticket**: grouped fields (system-generated read-only at top, classification
  fields, wide Summary/Description, attachments, primary/secondary actions), busy
  submit state, inline field-level validation, success state showing the generated
  Ticket Number.
- **My Tickets**: search box, filter dropdowns, sortable columns, pagination,
  loading/empty/no-results/error states, responsive card view under 768px.
- **Requester Ticket Detail**: read-only header fields, attachment list with
  add/download/remove actions, distinct removed-attachment styling.
- Responsive breakpoints and component states follow the Zen Green tokens table.

## 7. Data Changes
New Prisma models (see `server/prisma/schema.prisma`):
- **DevRequester**: `id`, `name`, `email` (unique), `isActive`, `createdAt`.
- **Ticket**: `id`, `ticketNumber` (unique), `requesterId` (FK → DevRequester),
  `categoryId` (FK), `relatedSystemId` (FK), `summary`, `description`,
  `requestedPriority` (enum: LOW/MEDIUM/HIGH), `itPriority` (enum, nullable),
  `currentStatus` (enum: NEW/OPEN/IN_PROGRESS/RESOLVED/CLOSED — only NEW used in Lab
  2), `createdAt`, `updatedAt`.
- **Attachment**: `id`, `ticketId` (FK), `originalFilename`, `storedFilename`,
  `mimeType`, `sizeBytes`, `uploadedAt`, `isRemoved` (default false), `removedAt`
  (nullable), `removedReason` (nullable).
- **Category** (extended from Lab 1): add `isActive`.
- **RelatedSystem** (new): `id`, `name` (unique), `isActive`, `createdAt`.

Relationships: one `DevRequester` → many `Ticket`; one `Ticket` → many `Attachment`;
one `Category` → many `Ticket`; one `RelatedSystem` → many `Ticket`. Indexes on
`Ticket.requesterId`, `Ticket.ticketNumber` (unique), `Ticket.currentStatus`,
`Attachment.ticketId`. Migration adds all new tables/columns without touching the
existing Lab 1 `Category` table's data.

## 8. API Contract
See `docs/lab-02/api-spec.md` for full detail. Endpoints:
`GET /api/categories`, `GET /api/related-systems`, `GET /api/dev-requesters`,
`POST /api/tickets`, `GET /api/tickets`, `GET /api/tickets/:id`,
`POST /api/tickets/:id/attachments`, `GET /api/tickets/:id/attachments`,
`GET /api/attachments/:id/download`, `DELETE /api/attachments/:id`.
All Requester-scoped endpoints require the `X-Dev-Requester-Id` header.

## 9. Acceptance Criteria
- AC-01: Given valid ticket data and 0–5 valid attachments, when the Requester
  submits Create Ticket, then one ticket is saved, a unique Ticket Number is
  generated, and the success state displays it.
- AC-02: Given no Development Requester is selected, when the user tries to open My
  Tickets or Create Ticket, then they are redirected to the Requester Selection
  screen.
- AC-03: Given Requester B is selected, when a ticket or attachment belonging to
  Requester A is requested by ID, then the API returns 404 and no data is returned.
- AC-04: Given the Summary field is empty, when the Requester submits the form, then
  a field-level validation message appears and no API call is made.
- AC-05: Given the Description is only 3 characters, when submitted, then a
  field-level validation error is shown citing the minimum length.
- AC-06: Given an unsupported file type (e.g. `.exe`) is selected as an attachment,
  when the Requester attempts to attach it, then the file is rejected client-side
  with a clear message and is not uploaded.
- AC-07: Given a valid 6 MB file is selected, when attached, then it is rejected for
  exceeding the 5 MB limit.
- AC-08: Given a ticket already has 5 active attachments, when the Requester tries to
  add a 6th, then the request is rejected with a clear message.
- AC-09: Given the backend is unreachable, when the Requester submits Create Ticket,
  then a safe error state is shown and all entered field values remain in the form.
- AC-10: Given a Requester has tickets, when they search by ticket number substring,
  then only matching tickets are shown.
- AC-11: Given a Requester filters My Tickets by Category = "Hardware", when applied,
  then only Hardware tickets are shown.
- AC-12: Given a Requester has more tickets than one page, when they page forward,
  then the next set of tickets loads and pagination controls reflect the current
  page.
- AC-13: Given a Requester has zero tickets ever created, when they open My Tickets,
  then the "no tickets yet" empty state is shown (not the no-results state).
- AC-14: Given a Requester has tickets but the current filters match none, when
  applied, then the distinct "no results" state is shown.
- AC-15: Given the selected Requester is switched from A to B, when My Tickets
  reloads, then Requester A's tickets are no longer visible and Requester B's tickets
  (if any) appear.
- AC-16: Given an owned ticket with an active attachment, when the Requester clicks
  download, then the file downloads successfully.
- AC-17: Given an owned ticket with a soft-removed attachment, when the Requester
  attempts to download it, then the request is rejected and no file is returned.
- AC-18: Given an owned attachment, when the Requester removes it and provides a
  reason, then it is marked removed, remains listed as metadata, and can no longer be
  downloaded.
- AC-19: Given the Development Requester list is loading, when the selection screen
  first renders, then a loading indicator is shown instead of an empty dropdown.
- AC-20: Given the viewport is under 768px, when My Tickets is viewed, then the list
  renders as stacked cards instead of a horizontally-scrolling table.

## 11. Assumptions and Decisions
- Attachments are stored on local disk under `server/uploads/` (not cloud storage),
  referenced by `storedFilename`; acceptable for this lab's local-only scope.
- The `X-Dev-Requester-Id` header (not a query parameter) carries the simulated
  identity, since it most closely resembles how a future `Authorization` header will
  work in Lab 3.
- Default page size is 10; sortable columns default to `createdAt DESC`.
- `RelatedSystem` is modeled as its own reference table (not a free-text field) for
  consistency with `Category` and to support future admin management.
- **[Approved]** The selected Requester is stored in `sessionStorage`, not
  `localStorage`: each new browser session/tab requires re-selecting a Development
  Requester, which better simulates a real login boundary and avoids a stale
  requester silently persisting across unrelated test sessions.
- **[Approved]** Ticket Number sequence resets per calendar year
  (`TKT-2026-000001`, `TKT-2027-000001`, ...). This requires computing the next
  sequence scoped to the current year at creation time inside a transaction to
  avoid collisions under concurrent submissions.
- **[Approved]** Unsupported attachment MIME type returns `415 Unsupported Media
  Type` (more semantically precise than a generic `400`); oversized files still
  return `413 Payload Too Large`; other field validation errors remain `400`.
