# Lab 2 — AI Use and Reflection

I used [Claude], with an AI Specification Agent phase (drafting
specification.md, tests.md, ui-spec.md, api-spec.md) followed by an AI Coding Agent
phase (implementation per approved contract).

## Selected Key Prompts
| Prompt Name | Actual Prompt Text | My Reflection |
|---|---|---|
| Evidence Gate | "Read the Lab 2 labsheet and current Lab 1 code. Report the baseline, constraints, and required Feature scope with citations. End with EVIDENCE GATE: PASS or BLOCKED." | Forcing the agent to cite the labsheet and the existing Lab 1 code before doing anything else caught scope confusion early — it made explicit what Lab 2 excludes (authentication, IT Staff workflow) instead of letting that boundary blur once coding started. |
| Draft Specification | "Draft docs/lab-02/specification.md covering FR, BR, UI summary, data changes, API contract, acceptance criteria, and Definition of Done for the TokTickIT Requester Ticketing MVP. Do not write code yet." | Writing the spec before any code existed surfaced decisions I hadn't consciously made yet — field length limits, what counts as a duplicate submission, how attachment removal reasons are validated. Deciding these on paper was much cheaper than discovering them mid-implementation. |
| Review Specification | "Act as a specification reviewer for specification.md. Report ambiguity, missing failure states, untestable wording, and conflicts with the labsheet, ordered by severity." | Having the agent adversarially review its own draft (rather than just asking "does this look okay?") caught vague acceptance criteria that weren't actually testable as written, and a couple of failure states I hadn't specified (what happens if attachment upload fails after the ticket itself was already saved). |
| Draft Test Plan | "Draft docs/lab-02/tests.md with a planned-test table and AC traceability matrix covering unit, API, UI, responsive, and E2E levels." | The AC-to-test traceability matrix was the most useful artifact of the whole sprint — it's what let me later prove, with real command output, which acceptance criteria actually had passing evidence versus which were only assumed to be covered. |
| Implement Development Requester Context | "Implement the DevRequester model, idempotent seed, active-requester API, and Selection screen. Label it clearly as a testing mechanism, not authentication." | Being explicit that this is a testing mechanism and not real auth kept the implementation honest — no password fields, no session logic snuck in, which made the Lab 3 migration path clearer. |
| Implement Create Ticket | "Implement only the Create Ticket screen and API per the approved contract, including attachment upload and validation." | Scoping the prompt to just Create Ticket (not "build the whole app") kept each implementation pass reviewable — I could check one screen against its acceptance criteria before moving on, instead of auditing a large diff touching everything at once. |
| Implement My Tickets | "Implement the requester-owned, paginated, searchable, filterable, sortable ticket list per the contract." | This prompt's implementation is where ownership scoping (a requester only ever sees their own tickets) had to be enforced server-side, not just hidden in the UI — reviewing the actual query logic, not just the rendered list, was necessary to trust that AC-15 was really satisfied. |
| Implement Ticket Detail + Attachments | "Implement the read-only Ticket Detail screen and the attachment add/download/soft-remove lifecycle, enforcing ownership server-side." | Later, real E2E testing revealed that the rendered DOM structure differs by viewport (table rows on desktop/tablet vs. card-links on mobile) — a detail the contract hadn't explicitly called out, which forced writing resilient selectors instead of assuming one layout. |
| Completion Review | "Audit the implementation against every acceptance criterion and planned test. Report missing evidence or skipped tests before claiming completion." | This is the prompt that mattered most for trust. The first real Playwright run failed for several unrelated reasons in sequence — missing browser binaries, missing system dependencies, ambiguous selectors, and stale/duplicated seed data — none of which a "looks done" claim would have caught. Later, comparing tests.md against actual `npm test` output also showed that a few planned tests (unit tests for the ticket-number generator, a route-guard test, an attachment-lifecycle E2E scenario) were never actually implemented, and a real mobile UI bug (header nav overlap) only surfaced during manual screenshot review, not through any automated test. |
## Reflection
_Having an explicit specification and test plan before implementation changed the working relationship with the AI agent: disagreements moved from "does this code work" to "does this match the approved contract," which was much easier to verify. The review/completion-audit step was the single most valuable habit — several real gaps (unimplemented unit tests, an unautomated attachment E2E scenario, a mobile UI bug) only surfaced because I asked the agent to check evidence against the plan rather than take its "done" at face value. Next sprint, I'd write the E2E test data-isolation strategy (unique identifiers, reseeding) into the test plan itself from the start, since debugging flaky parallel-run collisions after the fact cost more time than planning for it up front would have._
